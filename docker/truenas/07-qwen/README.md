# Qwen on Leo (initial trial)

Doco-CD discovers this stack from `docker/truenas/.doco-cd.yaml` when it lands on `master`; a draft PR does **not** deploy it. After merge, dexd registers `qwen.ishioni.casa` in UniFi DNS, and Traefik routes `https://qwen.ishioni.casa/v1` through the existing `apps` network. The `ishioni.casa` / `*.ishioni.casa` Let's Encrypt certificate is configured in `01-traefik/config/traefik.yml`. There are no published host ports.

The router accepts only source addresses in `10.1.0.0/16` (the observed NAS LAN is `10.1.2.0/24`). This is **network restriction, not user authentication**. Other trusted containers on `apps` can reach the server directly; do not publish or forward this API to the internet, or put it behind a public proxy. If clients use another VLAN/VPN range, add its _specific_ CIDR after checking the client address Traefik actually sees; do not remove the restriction for convenience. Never run untrusted MCP servers inside this container.

## Why this starting point

- `llama.cpp` already has an image pinned in the archived trial, an OpenAI-compatible chat API with native tool-call parsing, and a Vulkan backend. A one-off `--list-devices` test on Leo with **only** `/dev/dri/renderD128` exposed found `Vulkan0: AMD Radeon Graphics (RADV RENOIR)`. Ollama adds another daemon without a clear advantage here; ROCm support for this APU is uncertain. This is not a claim that Vulkan outperforms the CPU.
- [Qwen3-8B Q5_K_M](https://huggingface.co/Qwen/Qwen3-8B-GGUF/blob/main/Qwen3-8B-Q5_K_M.gguf) is a 5.85 GB download with instruction, coding and tool-call support. `--jinja` retains the model's own tool template; do not substitute generic ChatML. 8,192 tokens of context, one slot and four CPU threads start small; 16 GiB is a hard **container** limit, not a reservation or a measured peak. GPU allocations use shared system RAM, not separate dedicated VRAM. On first use the model is downloaded over the internet from Hugging Face into the existing SSD cache (`/mnt/SSD/docker-applications/llamacpp/cache`); old cached models are not removed. It unloads from memory after five idle minutes, then reloads on the next request.
- ZFS ARC was ~6.4 GB during inspection, with a configured 4 GiB minimum and 32 GiB maximum; no ARC or power script changes are proposed initially. ARC is reclaimable, but check host pressure and the HAOS VM during testing. The GPU's reported ~32 GiB Vulkan heap is **not** an extra 32 GiB of RAM.

MCP tools should live in your agent client (e.g. a workstation agent with its existing MCP configuration). Point its OpenAI-compatible model provider at `https://qwen.ishioni.casa/v1`, select model `qwen3-8b-q5-k-m`, and let the client send tool definitions and execute returned calls. The model server itself does not get shell, filesystem, Docker socket or MCP credentials. Client compatibility and multi-step tool calls still need an end-to-end test. If your client insists on an API key, a dummy value is enough for an unauthenticated endpoint; it does **not** provide security.

## After merging: check, measure, then iterate

1. Confirm the Doco-CD target discovered and started `qwen`. Watch `docker logs -f qwen` for model download, GPU layer offload and readiness; first startup may take minutes. From an allowed LAN client: `curl -fsS https://qwen.ishioni.casa/health` and `curl -fsS https://qwen.ishioni.casa/v1/models`. Check TLS is trusted and the DNS address resolves to the internal Traefik entrypoint, not a WAN proxy. Confirm a client outside the allowlist gets 403.
2. From an allowed client, send a representative infrastructure prompt and a tool-call request, then complete the tool response through your MCP-capable agent. For example, request a harmless tool (such as returning the current time) and confirm `tool_calls` and the follow-up answer; do **not** grant the model production-changing tools until reviewed. Record cold-load time, prompt and generation token rates, tool-call reliability, and `docker stats --no-stream qwen` along with host `free -h` and `/proc/spl/kstat/zfs/arcstats` under load. `docker stats` does not capture all shared GPU/ARC effects: watch host memory too.
3. Compare identical prompts with a CPU-only trial: set `--device none` in the server command (merely setting GPU layers to 0 can still touch the GPU), remove the render-device mapping, and re-deploy through a reviewable Doco-CD change. If Vulkan is slower or unstable on Vega, keep the CPU configuration. Only then consider 16K context, Qwen3-14B Q4_K_M, or a coding-specific model; measure memory and latency again before raising the cap. If memory pressure appears, reduce context/offload/cache before touching ARC limits or `powersave.sh`.

This PR does not run the model, measure inference speed or change the TrueNAS power/ZFS settings. Merging into `master` **will** trigger Doco-CD deployment during reconciliation; review the LAN CIDR, model download and memory budget first.
