# llama-modchip on Leo: isolated trial (not a deployment)

**Status:** exploratory draft, independent of the [Gemma deployment PR #6221](https://github.com/ishioni/homelab-ops/pull/6221). This file is directly under `docker/truenas/`, **not an auto-discovered Doco-CD stack**. Nothing here changes the Gemma PR or authorizes an infrastructure agent to act unattended.

## Hardware and safety boundary

Leo runs TrueNAS 25.10.7 on a Ryzen 5 PRO 5650G (**Zen 3, six physical cores / 12 threads, AVX2/FMA/F16C, no AVX-512**) with 64 GiB DDR4 ECC, ZFS, Docker and a HAOS VM. The Vega iGPU shares system RAM. The tested modchip path is **CPU-only**, with 16K context, four server threads and a four-CPU container quota; it does not use Vulkan. Leo's persistent ZFS ARC maximum remains **16 GiB** (minimum 4 GiB). The test container had a **30 GiB hard memory/swap limit**, no added capabilities or privileges, read-only root filesystem and model mount, no Docker socket, no gateway or agent tools, and only `127.0.0.1:18081` published on Leo. A separate remote watcher sampled host `MemAvailable` every five seconds and would stop the server below 8 GiB. It did not trigger. No host package, THP, power, systemd or ZFS settings were changed by this trial.

The repository's DeepSeek-V4-Flash 284B option is **not a fit**: its claimed ~57–59 GiB process residency would leave inadequate room for ZFS, HAOS and other services, exceeding the agreed 32 GiB inference budget. Headline Zen 5 AVX-512, discrete-GPU and high-core-count results do not predict this Zen 3 / DDR4 host's performance.

## Pinned inputs and method

- [`synchopate/llama-modchip` source](https://github.com/synchopate/llama-modchip/commit/1d7eb703629bd0cee9fb0014d79e4d1ed28b9d2a) `1d7eb703629bd0cee9fb0014d79e4d1ed28b9d2a`, Nemotron patch `patches/zen5-nemotron-256k-optimizations.patch`, and its four `speculative/cpp` support files applied to [upstream llama.cpp](https://github.com/ggml-org/llama.cpp/commit/d2f83055d6e3b379b5d34c4837122a918cf402c2) `d2f83055d6e3b379b5d34c4837122a918cf402c2`. Built inside a disposable Debian Docker build with `GGML_NATIVE=OFF`, AVX2/FMA/F16C and OpenMP enabled, no CUDA/Vulkan, and four build jobs. The first Docker build failed because the throwaway build stage lacked `git`; adding that build dependency succeeded. **Neither `install.sh` nor `./modchip` was run.** The compiled binary was not a downloaded release executable.
- [Official ggml-org Nemotron-3.5-Lightning-30B-A3B `Q4_0` GGUF](https://huggingface.co/ggml-org/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-GGUF/resolve/8cd082170ed313484be1cf44f256a5caa2cfdad3/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-Q4_0.gguf), revision `8cd082170ed313484be1cf44f256a5caa2cfdad3`, 18,898,091,584 bytes (~17.60 GiB). Downloaded on Leo and verified SHA-256 `61f87e75974e4b535dcdf9aad056541a9514f1dfa4538b463b081d19b7a00e3c`. Its upstream license is [OpenMDW-1.1](https://openmdw.ai/license/1-1/); a derived model card marking itself MIT does not supersede upstream terms.
- The same GGUF was also run using pinned, unpatched `ghcr.io/ggml-org/llama.cpp:server-b9570` CPU for a **same-model engine control**. Both servers used the same 16K context, four threads/CPU quota, one slot, no prompt cache, temperature 0, seed 42, thinking disabled in the requests and a 1,000-token output cap. The two requests included the same repository-grounded TrueNAS Compose/YAML and RustFS OpenTofu context used in PR #6221 (about 2.6K and 1.5K Nemotron prompt tokens). One request per engine/task: **these are samples, not medians or a quality benchmark**.
- The patched engine was also tried with its **online `ngram-simple` speculation** (`--spec-type ngram-simple`, N=4, M=7, min-hits=1) but without trained RouteCrack tables (startup reported zero cascade tables, hot rules and macro entries). This is **not** the repository's claimed fully trained 60 tok/s Stockfish-PVS configuration. This run also changed output lengths, so equal wall times are not an apples-to-apples throughput comparison.

| Engine / task                      | Prompt tokens | Prompt tok/s | Generated tokens | Generation tok/s | Wall time |
| ---------------------------------- | ------------: | -----------: | ---------------: | ---------------: | --------: |
| Stock Nemotron Q4 / YAML           |         2,647 |         51.7 |              543 |             12.4 |      96 s |
| Patched Nemotron Q4 / YAML         |         2,647 |         51.5 |              544 |             12.4 |      96 s |
| Patched + online n-gram / YAML     |         2,647 |         51.8 |              680 |             17.9 |      90 s |
| Stock Nemotron Q4 / OpenTofu       |         1,527 |         52.3 |              504 |             12.8 |      69 s |
| Patched Nemotron Q4 / OpenTofu     |         1,527 |         52.4 |              506 |             12.7 |      69 s |
| Patched + online n-gram / OpenTofu |         1,527 |         52.3 |              385 |             13.0 |      59 s |

The patched CPU-only run's sampled minimum host `MemAvailable` was ~18.8 GiB; the online n-gram run's was ~18.2 GiB. Container `docker stats` ranged from ~16.3 to ~19.8 GiB across the trials; file cache accounting differs, so these numbers are **not** a direct model-to-model peak-RAM ranking. All three servers fit their 30 GiB cgroup ceiling and had no observed OOM. The n-gram engine logged draft acceptance of 340/355 (~95.8%) on the repetitive YAML response but only 32/45 (~71.1%) on OpenTofu. Its speedup was workload-dependent, and its outputs were not identical.

**Correctness gate failed:** both ordinary and speculative Nemotron YAML answers defined `qwen-lan` but omitted `traefik.http.routers.qwen.middlewares: qwen-lan`, leaving the requested LAN allowlist **unapplied**. Both OpenTofu callers omitted the explicitly requested `versioning = true` despite describing it in prose. Speculation did not cure either mistake, and some validation advice was misleading. These are safety-relevant failures for the intended infrastructure use; faster decode on one repetitive response does not make this a better supervised agent than Gemma/Qwen. For reference, prior Leo single-run figures under the same 16 GiB ARC cap put CPU Qwen at ~9.6/12.6 generation tok/s on YAML/OpenTofu and Gemma Vulkan at ~9.7/9.8, with different token counts and outputs. A fair quality decision requires more held-out tasks and a tool-result round trip.

## Fractal-64 custom quantization and cleanup

The project's [Fractal-64 Nemotron GGUF](https://huggingface.co/Synchopate/NVIDIA-Nemotron-3.5-30B-A3B-Fractal-64-CPU-GGUF/resolve/61b06d0d3ddd8255cc408ebc444cd78ecfc591f5/NVIDIA-Nemotron-3.5-30B-A3B-Fractal-64.gguf) (revision `61b06d0d3ddd8255cc408ebc444cd78ecfc591f5`, 15,420,034,624 bytes / ~14.36 GiB) was downloaded and verified SHA-256 `71c22562ab908d5d3373e3a010544e977af2499e3cc476fc7646d402a8a550ee`. SSH-agent signing briefly failed during setup but later recovered. The **same patched AVX2 server** successfully loaded the custom GGUF and completed both prompts, with a 28 GiB Docker limit and no speculation. Fractal-64 `Q2_0` tensors require a compatible patched engine; do not load this GGUF with stock llama.cpp.

| Fractal-64 task | Prompt tokens | Prompt tok/s | Generated tokens | Generation tok/s | Wall time |
| --------------- | ------------: | -----------: | ---------------: | ---------------: | --------: |
| YAML            |         2,647 |         36.6 |              824 |             14.3 |     131 s |
| OpenTofu        |         1,527 |         36.5 |              489 |             14.9 |      75 s |

The minimum sampled host `MemAvailable` was ~33.0 GiB, and container-reported usage after the requests was ~15.7 GiB / 28 GiB; there was no observed OOM. Compared with the official Q4 on the patched engine, Fractal-64 reduced model/disk footprint and raised decode from ~12–13 to ~14–15 tok/s, but **slowed prompt processing from ~52 to ~37 tok/s**. The sample wall times were longer because output lengths also changed; this does not establish a general speed or quality ranking. It **still failed the correctness gate**: the YAML bound the model to `127.0.0.1` inside the container (unreachable from Traefik), omitted router attachment of the defined LAN allowlist, and then falsely claimed the allowlist was active. The OpenTofu caller again omitted `versioning = true` while claiming versioning was enabled. Do not treat the custom quant's smaller size as evidence of safe infrastructure answers. The derived Hugging Face card's MIT label should be reconciled with the upstream model's OpenMDW-1.1 terms before redistribution.

The prior manual `qwen-bench-coder-final` container and `/mnt/SSD/docker-applications/qwen-bench` cache were removed without touching the proposed GitOps Gemma cache or Doco-CD. **After all four modchip/stock trials, Leo cleanup was verified:** `modchip-leo-bench`, `nemotron-stock-bench`, `modchip-spec-bench`, and `modchip-fractal-bench` were removed, as were the dedicated `/mnt/SSD/docker-applications/modchip-bench` directory (including both GGUFs and source) and `modchip-leo-trial:avx2` image. No inference test container remains. Docker's shared build cache was not globally pruned because that could affect unrelated projects; ZFS space accounting may lag deletion.

The project launcher can start a gateway and uses non-isolated ports; `modchip claude` includes `--dangerously-skip-permissions`. This trial did not run the launcher, gateway, tools, or released binaries, and should not be promoted to a deployable Doco-CD stack based on these measurements.
