# Internal CA and Dragonfly certificate

Flux installs cert-manager and External Secrets first, then reconciles `internal-ca`. The `internal-ca` Kustomization creates the CA, the scoped Kubernetes-backed ClusterSecretStore, and its reader RBAC. Application Kustomizations own their own public-CA ExternalSecrets. Neither the Dragonfly listener nor any clients switch to TLS in this PR.

The self-signed `security/internal-ca` Certificate stores the CA certificate and signing key in `security/internal-ca-key-pair`. The `internal-ca` ClusterIssuer signs certificates in other namespaces; restrict who can request them and back up the signing Secret. The CA is valid for 10 years and renews one year before expiry, retaining its private key. The Dragonfly Certificate now lives alongside the Dragonfly cluster in `kubernetes/apps/database/dragonfly/cluster/certificate.yaml` and produces `database/dragonfly-server-tls`. Its DNS SANs cover `dragonfly`, `dragonfly.database`, `dragonfly.database.svc`, and `dragonfly.database.svc.cluster.local`; it lasts 90 days and renews 15 days before expiry with a new key.

ESO authenticates as `security/internal-ca-reader`. Its Role permits `get` on only the named CA source Secret, but that grants access to the **whole source object**, including the signing key. Each application ExternalSecret copies only `tls.crt` under the public key `ca.crt`, refreshed hourly. ToolHive and Renovate use `internal-ca` in `ai` and `github`; Immich, Paperless, and SearXNG use distinct `immich-internal-ca`, `paperless-internal-ca`, and `searxng-internal-ca` Secrets in `selfhosted`. No private key is distributed. This is not a combined public-root store: Node's `NODE_EXTRA_CA_CERTS` extends its default roots, and Python Redis clients use the CA file for Redis TLS only. ToolHive can use the `ai` Secret via `caCertSecretRef`.

## Verify before the TLS cutover

Check readiness of the Flux Kustomizations, both ClusterIssuers, both Certificates, the ClusterSecretStore, and all five application ExternalSecrets. Confirm `security/internal-ca-key-pair`, `database/dragonfly-server-tls`, and the five target CA Secrets have the expected keys without printing the signing key. Check the leaf certificate SANs, chain and expiry, and confirm each target's `ca.crt` matches the source `tls.crt`. Flux readiness here means the manifests applied, not that certificates have been issued or ESO has replicated the CA. Check the actual resources before merging the TLS cutover.

After the later TLS cutover, Dragonfly does not automatically reload a renewed TLS Secret; reload and verify the served certificate on each pod. Some clients cache CA roots; ToolHive uses a `subPath` mount and needs a restart after CA changes. Monitor CA and leaf expiry. cert-manager CA issuers do not automatically reissue leaves when their CA changes. For CA replacement, distribute overlapping old/new trust, reload clients, reissue and reload leaves, and remove old trust only after testing. This single-source ESO replication does not implement overlap automatically.
